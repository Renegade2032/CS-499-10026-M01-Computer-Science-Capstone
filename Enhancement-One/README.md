# Enhancement One: Software Design and Engineering
1. Artifact Description
The artifact I chose for this milestone is an Android inventory tracking app that I made earlier in the Computer Science program. The app was originally made to keep track of inventory, but for this enhancement I wanted to take what I already had and turn it into something that could be used for a computer repair business.
I still wanted to keep the inventory part because a repair shop would need to keep track of parts. What I wanted to add was a way to also keep track of customer repairs. My idea is to eventually have one app where I can manage both the parts I have and the computers that are being repaired.
2. Why I Selected This Artifact and What I Improved
I picked this project because I already had a working starting point and I wanted to see how much I could add to it without rebuilding the whole thing. I also wanted the enhancement to be more than just changing the colors or layout. I wanted to actually add something new that the app could do.
The first thing I added was a dashboard. From the dashboard I can choose New Repair, Existing Repairs, or Parts Inventory. This made it easier to separate the repair side of the app from the inventory side while still keeping everything together in one application.
After that I worked on the New Repair screen. This is where information about a customer's computer can be entered. I added fields for the customer's name, phone number, device type, manufacturer or model, problem description, repair status, and technician notes. I also added different statuses that I would expect to use while working on a repair. These include Received, Diagnosing, Waiting for Parts, In Repair, Ready for Pickup, and Completed.
I also added some checks to the New Repair screen. I did not want a repair to be entered with important information missing, so the app checks things like the customer's name, phone number, device information, and problem description.
The Existing Repairs screen was another part that I worked on. I was able to get the repairs I entered to show up on this screen. I also started building a Repair Details screen. The idea behind this screen is that I will eventually be able to select one of the repairs, see all of its information, and update it when something changes.
I also created separate classes for the repair tickets and the repair repository. This was something I needed as the project started getting bigger because I did not want all of the repair code sitting inside one activity.
3. Course Outcomes
This enhancement helped me work toward the software design and engineering course outcome because I had to take an application that was already built and figure out how to add more functionality to it. I could not just treat it like a brand-new project because I still wanted the original inventory system to work.
I worked with Kotlin, Java, Android Studio, and XML while making these changes. I also had to work with several Android activities and figure out how to move between the different screens. As I added more features, I had to think more about how the information should be organized instead of just getting something to appear on the screen.
The project also gave me a chance to work on designing a solution for a real problem. A computer repair shop needs to know what repairs it has, what stage those repairs are in, and what parts are available. Instead of creating two completely separate apps, my goal is to put those things together.
I have not finished everything yet. One of the bigger things that still needs work is saving the repair tickets permanently. Right now I can create repairs and see them under Existing Repairs, but they are being stored in memory in the repair repository. If the app is completely restarted, that information can be lost. One of my next changes will be connecting the repair system to the database so the repair tickets can be saved.
4. Reflection
A lot of this milestone was figuring things out as I went. Some parts worked the way I expected, while other parts caused errors that I had to go back and fix. I had problems with XML layouts, resource IDs, Kotlin code, buttons, and getting the different activities to work together.
One problem I had was with the Back button on the New Repair screen. The button showed up, but clicking it did nothing. When I went back through the Kotlin code, I found that I had put the click listener in the wrong place. After moving it, the Back button started working.
I ran into more problems when I started working on the repair list and Repair Details screen. At different points I had code in the wrong file, problems with classes, and errors because I was trying to change values that could not be changed. These were frustrating at first, but fixing them helped me understand the way the different Kotlin classes and Android activities are connected.
I also learned that getting something to work on the screen does not always mean that part of the application is finished. I got Existing Repairs working and could see the repairs I entered. Later I realized that I was storing them in a mutableListOf inside RepairRepository. That works while the information is still in memory, but it is not permanent storage. I decided that getting the database storage working would be a good next step instead of trying to force it into this milestone before the rest of the repair system was ready.
The main thing I got out of this enhancement was experience taking something I already built and adding onto it. I started with an inventory tracking app, and now it is starting to become more of a PC repair management app. It is not finished yet, especially the Repair Details and permanent storage parts, but I have a working base that I can continue building on.

# Algorithms and Data Structures Enhancement
1. Artifact Description
For this milestone I continued working on the Android inventory app that I made in CS 360: Mobile Architecture and Programming. In Milestone Two I started changing the inventory app into a computer repair management app. I wanted to keep working with the same app because it is something I could see myself actually using if I had a computer repair business.
The repair part of the app now lets me make a repair ticket and save the customer's name, phone number, device type, model, problem, status, technician notes, and priority. I also connected the repairs to the SQLite database. Before doing this I was using a list in memory, which meant the repair information would not be something I could depend on after closing the app. Now the repair records can stay saved after the app is closed and restarted.
2. Why I Selected This Artifact and What I Improved
I chose to keep using this artifact because I could add the algorithms and data structures work to something I had already been building. I think this made more sense than making another program just to show sorting and searching. If this was being used in a repair shop and there were a lot of repair tickets, I would need a quick way to find the one I was looking for.
I added a search that can look through the customer name, phone number, and device information. I also added a status filter. The repair can be Received, Diagnosing, Waiting for Parts, In Repair, Ready for Pickup, or Completed. This way if I only wanted to see the computers that are waiting for parts, I could choose that status instead of looking through every repair ticket.
I also added Low, Normal, High, and Urgent for the repair priority. Then I added sorting so I can put the higher priority repairs first. The app takes the repair records and makes a filtered list depending on what I search for, the status I choose, and the sort option. I think this makes the repair list a lot easier to use than just showing every repair in the order it was entered.
Another part I worked on was saving the repairs. I changed the repair repository so it uses the SQLite database instead of only keeping a temporary list in memory. Each repair now gets a database ID. I needed this so when I change a repair the app knows which saved repair needs to be updated. I also decided I do not want completed repairs deleted. I would rather keep them because if the same customer brings the same computer back later, I could look back and see what was already done to it.
3. Course Outcomes
I think this enhancement mainly works with Course Outcomes 3 and 4. For Course Outcome 3 I used searching, filtering, sorting, and collections to work with the repair information. I had to think about how these things should work together. For example, I can search for a customer and still use the status filter and priority sorting on the results. This helped me understand more about how an application can organize information instead of only saving it and putting it on the screen.
For Course Outcome 4 I used Kotlin, Java, XML, Android Studio, and SQLite while working on the app. I was not just adding something that would not be used. Searching for a customer, seeing which repairs are waiting for parts, and putting an urgent repair first are things I think would actually help in a computer repair business. I also had to make the new work fit with the code I already had instead of starting the application over.
4. Reflection
One thing I learned while doing this is that one change can turn into changes in a lot of different places. When I added priority I first thought it would mainly be adding the choice to the repair. I ended up having to change the RepairTicket class, New Repair screen, Existing Repairs screen, Repair Details screen, repository, and database so all of them used the priority correctly.
I also ran into a few problems. One was when the priority dropdown was on the screen but nothing showed up when I clicked it. I found out the adapter code was in the wrong place. I also had problems when I changed the repository from the temporary list to SQLite. Once I added an ID to each repair it made more sense how I could update the correct repair in the database.
I worked on one part at a time and ran the app to see what happened. I tested the search, status filter, priority sorting, and editing. I also closed and restarted the app to make sure the repair was still there. When something did not work I went back to the part I had just changed. This helped me find the problem instead of changing a bunch of things at the same time and not knowing which change caused it.
After working on this milestone I can see why searching and organizing the data becomes more important as more information is saved. A small repair list is easy to look through, but that would change if there were a lot of customers. I think the app is closer now to something that could actually be useful for keeping track of computer repairs. It also helped me see how the screen, the repair objects, the repository, and the database all have to work together.
